# TIM.EXE 1.11 - The Even More Incredible Machine

The reconstruction's target since 2026-09-30. 1.00 (`incredible-machine/`) is
reconstructed and tagged `tim-1.00`; this is what is known about 1.11, the
executable GOG ships as The Even More Incredible Machine (installer 2.1.0.24,
extracted into `even-more-incredible-machine/`, which is not tracked).

## The file

`TIM.EXE`, 114,652 bytes, dated 17 Nov 1993. The data files are dated 26 Jul
1993 and the level count is 160 (`L1.LEV`..`L160.LEV` are probed; 1.00 probes
87). The executable says "This is version 1.11 of 'The Incredible Machine.'".

## Recovering the image: `tools/unrnc.py`

1.11 is **RNC ProPack method 1, twice, both layers keyed** - not LZEXE. The
outer layer is 117,412 bytes unpacked and holds the inner layer and its DOS
stub; the inner layer is the program, 220,992 bytes (0x35f40), which is its
whole memory image: the stack at `35ec:0080` ends exactly there.

Running the stubs under the emulator, as `tools/unlzexe.py` does for 1.00,
does not work: both come out with output that changes with the load address
and matches no CRC. The stub makes no DOS call, so it is the CPU emulation
that goes wrong somewhere; it was not chased. `tools/unrnc.py` decodes the
format instead and is held to RNC's own CRCs, which both layers pass:

- the key is the word after the 18-byte header, with bit 1 the "keyed" flag:
  0x664e is key 0x664c (outer), 0xfffe is 0xffff (inner);
- literal bytes are XORed with the key's low byte; the key is rotated right
  twice before the first run and once after every non-empty run;
- the bit stream starts after the key word, and its first two bits are
  skipped.

The entry (`0000:0000`), the stack and the **2,758 relocations** come out of
the inner stub: the fields at its cs:0, and the table at its cs:0x29a that the
stub walks - a byte count (0 ends), a segment word, then that many byte-sized
steps of the offset. Every relocated word is a segment inside the image; the
largest is 0x2fe1, DGROUP's.

## The layout

DGROUP is at 0x2fe10 (1.00: 0x2d3c0): the code is about 10.8 KB larger and
the initialised data about 4.9 KB smaller. The C startup and the copyright
string are the same.

## RESOURCE.CFG

**1.11's TIM.EXE reads RESOURCE.CFG as 1.00 does: three bytes**, the first
ignored, then the music device and the digitised module. GOG ships a
181-byte *text* file (`soundDrv = SBPRO.DRV`, `audioDrv = AUDBLAST.DRV`, ...)
in the format of Sierra's driver loader, which TIM.EXE does not read as text:
it takes " so" as device 0x73 and module 0x6f, past the ends of both tables.
Under the emulator that led the Sound Blaster module's IRQ probe to restore
IRQ 0's vector from a copy it never saved, which zeroed INT 8's vector; the
game's timer handler then chained to 0000:0000.

A copy of the game directory with a three-byte RESOURCE.CFG (`00 00 fe`: PC
speaker, no module) runs: the title (flip 120) and the credits (flip 450)
draw, 475 flips in 250M instructions. The `.DRV` names in the image's strings
(`STD.DRV`, `SBPRO.DRV`, `AUDBLAST.DRV`, ...) and the `SoundDrv`, `VideoDrv`,
`MouseDrv`, `JoyDrv`, `MemoryDrv` names are what 1.11 knows; which of them the
game loads, and from where, is not established yet - a run opens `VM.OVL` and
`SX.OVL` (from the resource archive) and no `.DRV` file.

## How far 1.00's source is from it

Matched routine by routine (1.00's 1,157 public routines from the link map,
immediates, displacements, call targets and relocated words masked), in
TEMIM's image:

| | routines |
| --- | --- |
| byte-identical, moved | 160 |
| same instructions, other addresses and constants | 354 |
| the same logic compiled differently | ~570 |
| no good match | 41 |
| too short to place | 29 |

"Compiled differently" is mostly code generation, not game changes: in
`part_hit_bellow` the logic and the record offsets are the same, and 1.11
merges two identical tails and returns early, which is jump optimisation
(`-O`) or a later compiler. It is spread over every segment, part kinds
included. The 41 are mostly the compressors' writers (`lzss_flush`,
`lzw_flush`, the Huffman encoder, `insert_node`/`delete_node`), and
`part_handle_at_pointer`, `part_key_shortcut`, `settle_carried_part` and some
sound routines.

New in 1.11, from its strings: "ADJUST PARTS BIN", "CLEAR PARTS BIN" with a
confirmation, "(Click here to enter description)", a data-disk check, the
named driver types above, `dynamix.pal`/`dynamix.scr` in place of `sierra.*`,
`gp_go.bmp`, and 560K of free memory where 1.00 wants 550K.
