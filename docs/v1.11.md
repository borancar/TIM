# TIM.EXE 1.11 - The Even More Incredible Machine

`reconstruct/v1.11`, beside 1.00's `reconstruct/v1.00` (`docs/v1.00.md`);
what both share is `docs/executable.md`. This is what is known about 1.11,
the executable GOG ships as The Even More Incredible Machine - installer
2.1.0.24, which the tree's `get-game.sh` extracts into
`reconstruct/v1.11/game/`, untracked. Its recovered image is
`out/v1.11/TIM.img`, and the tools work on it by default (`TIM_VERSION`).

## The file

`TIM.EXE`, 114,652 bytes, dated 17 Nov 1993. The data files are dated 26 Jul
1993 and the level count is 160 (`L1.LEV`..`L160.LEV` are probed; 1.00 probes
87). The executable says "This is version 1.11 of 'The Incredible Machine.'".

## Recovering the image: `tools/unrnc.py`

1.11 is **RNC ProPack method 1, twice, both layers keyed** - not LZEXE. The
outer layer is 117,412 bytes unpacked and holds the inner layer and its DOS
stub; the inner layer is the program, 220,992 bytes (0x35f40), which is its
whole memory image: the stack at `35ec:0080` ends exactly there.

Running the stubs under the emulator, as `tools/unlzexe.py` does for 1.00,
does not work: both come out with output that changes with the load address
and matches no CRC. The stub makes no DOS call, so it is the CPU emulation
that goes wrong somewhere; it was not chased. `tools/unrnc.py` decodes the
format instead and is held to RNC's own CRCs, which both layers pass:

- the key is the word after the 18-byte header, with bit 1 the "keyed" flag:
  0x664e is key 0x664c (outer), 0xfffe is 0xffff (inner);
- literal bytes are XORed with the key's low byte; the key is rotated right
  twice before the first run and once after every non-empty run;
- the bit stream starts after the key word, and its first two bits are
  skipped.

The entry (`0000:0000`), the stack and the **2,758 relocations** come out of
the inner stub: the fields at its cs:0, and the table at its cs:0x29a that the
stub walks - a byte count (0 ends), a segment word, then that many byte-sized
steps of the offset. Every relocated word is a segment inside the image; the
largest is 0x2fe1, DGROUP's.

## The layout

DGROUP is at 0x2fe10 (1.00: 0x2d3c0): the code is about 10.8 KB larger and
the initialised data about 4.9 KB smaller. The C startup and the copyright
string are the same.

| | |
| --- | --- |
| DGROUP | image 0x2fe10 |
| Borland's runtime (`CM.LIB`) | from 0x0c840 (`atexit`) |
| `vm_set_display_lines` | 0x09c2d |
| `vm_init`, `detect_adapter` | 0x2410d, 0x2425c |
| `open_bit_reader`, segment 248f's first routine | 0x26588 |

## What built it

Borland C++ 3.0 for the game's own modules, options per module, rebuilt with
`-O -Z` on top of 1.00's; **Borland C++ 3.1** for the sound library;
Borland C++ 2.0 for the older shared modules; Turbo C++ 1.01 for
`atan2_long`; TASM for the assembly. Each file's `JUDGE:` markers say which,
and `docs/executable.md` how it was measured.

### Compiler options

1.11's modules were rebuilt with **`-O -Z`** - jump
optimisation and redundant-load suppression - on top of 1.00's options.
Measured file by file with 1.00's sources (every routine judged with the
file's own options, then with `-O`, then with `-Z` added):

| | routines matching |
| --- | --- |
| 1.00's options | 339 of 1,079 |
| `-O` added | 433 |
| `-O -Z` added | 531 |

`game.c` goes from 3 of 57 to 51, `machine.c` from 13 of 75 to 50. The new
key filter at 0x0905a (below) matches only with `-O`. Three files do
*worse* with `-O` - `fstring.c` (7 of 7 without it), `mono.c` (6 of 6) and
`rects.c` - and keep 1.00's options: their objects look reused unchanged.
`resource.c` too. The modules 1.00 built with `-G -O` did not move either
way. Where `-O` or `-Z` tied, the file takes them, as the build as a whole
did; each is a measurement to revisit when its routines are transcribed for
1.11. `-d` is gone from `intro.c`: its pool holds "corners.bmp" twice.

### The sound library

**1.11 links each module of the sound library into a segment of its own**,
where 1.00 put all of the library's C into segment 2619. So the far calls
into it say exactly where each module begins, which 1.00's layout left to
inference: 26 C modules, now `reconstruct/v1.11/src/sound/`, one file each and
named for their first routine, plus `sound_data.c` - the bank record, the
voices and the five-tick wait, a module with no code whose place is its
data's. The assembly (`sound.c`, segment 2893) moved its far entry points
to its front and gained eleven, one for each API function 0x0a..0x17 the
dispatcher reaches; nothing calls them.

**The C is Borland C++ 3.1's, `-O2`** (`JUDGE: compiler bc3.10`), where
the rest of the game is 3.0's. 3.0 reproduced most of it but not all: it
dropped the loops' counter that 3.1 keeps stepping, and where 3.1 pushes
the high word of a far pointer it has just stored straight from DX, 3.0
reads it back from memory - in the game's own 3.0 code that read is always
from memory, and only the sound library's five sites use the register. No
combination of 3.0's switches gave either; 3.1 matches every module of the
library with the sources as they stood (one declaration moved in
`start_sequence_by_id`). 1.00's library is 3.0's: Dynamix rebuilt it with
3.1 for 1.11. BC++ 3.1 is turboc's `bc3.10`, `dos-c/BCPP310`.

`alloc_for_kind` and `free_for_kind` left the library: they are a module
after game.c in segment 0ecc (`kindmem.c`, no `-O`). `load_sound_bank`'s
`GMD:` case, which fell through to `default` in 1.00, has its `break`.

### The resource modules

**1.11 reads resources and writes none.** The writing side 1.00 carried and
never called is gone: `store_flush`, the run-length and LZW coders of
resfile.c (`lzw_open_write*`, `lzw_flush`, `output`, `long_div`,
`cl_block`, `cl_hash`, `rle_flush`, and their data), and LZHUF's encoder
(the trees, `huff_putcode`, `encode_*`, `lzss_open_write`, `lzss_flush`,
`putbuf`/`putlen`). The handler table keeps its seven words per type, the
flushes and opens null.

- **resource.c** (22 of 22, data and BSS) is BC++ 3.0 without `-O` where
  1.00's was 2.0. Its state is **separate variables**, byte-aligned, where
  1.00 had a stream record and a flags record: `g_stream_*`,
  `g_resource_*`, `g_lzw_*`, DGROUP 0x53a2..0x54ce, one byte at 0x54b5 that
  no instruction names. `emit_byte` steps its huge cursor with inline
  `asm` (`inc bx / jne / add seg, 0x1000`) that the compiler assembled
  itself: through TASM three other routines come out differently.
- **lzhuf.c** (10 of 10) is still TASM, redrafted from the image: two
  hand-written routines in front - `huff_get_bit` with no frame, and
  `decode_char`, LZHUF's `DecodeChar` with `update` folded in - then
  compiler output without `-O` for the rest.
- **resfile.c** is BC++ 3.0 without `-O`, 7 of 8. `write_resource`, which
  nothing calls, keeps its buffer in DI and uses SI only as a scratch
  register for the source pointer; no declaration tried (`register` on each
  local and parameter, an unused `register` in either order, `-rd`) puts the
  buffer in DI with SI free.
- **lzw.c** (TASM) names the new variables where it named record fields.

### Other modules

- `gamedata.c`'s tables end at 0x14eb; the pad byte there starts the
  strings' own object, `messages.c` (0x14ec..0x1d3c).
- `draw_xor_rect` (0x0a866) is a module of its own (`xorrect.c`): built
  without `-O` or `-Z`, where gamefile.c before it has both.
- `dos.c`'s interrupt stack has 0x400 bytes below its top (1.00: 0x100).
- `screenshot.c` is BC++ 2.0 without `-O`.
- `glue.c`'s wrappers are at 0x0c7da..0x0c840, and Borland's `atexit`
  follows at 0x0c840.

## The copy protection

GOG's 1.11 is cracked, but not as the 1.00 copy was. `copy_protect_screen`
still asks and still waits; after the third pick, where the original starts
the slots over -

    0fcf4  ff46f2         inc  word [bp-0xe]        slot++
    0fcf7  837ef203       cmp  word [bp-0xe], 3
    0fcfb  7505           jne  0x0fd02
    0fcfd  c746f20000     mov  word [bp-0xe], 0     slot = 0

- the crack wrote `eb 51` over the `mov`'s first two bytes and `00` over its
third: `jmp 0x0fd50`, which is `done = 1`. So any three parts pass, on the
third click. The two zero bytes after it are the `mov`'s immediate, left
behind. The original bytes are 1.00's same instruction (`c7 46 f0 00 00` at
0x0ed8a) with 1.11's slot offset. `tools/uncrack.py`'s `CRACKS` holds each
version's crack by the size of its image, and the judge and `tools/link.py`
put 1.11's three bytes back, as they do 1.00's one, and build with
`TIM_COPY_PROTECTION`. The source's default is the crack - `goto check`
after the third pick, and the two bytes it left behind as `asm db` - which
the judge's `--cracked` proves against the shipped bytes.

Because 1.11's screen waits, the developer build's autoplay (`TIM_LEVEL`,
`TIM_RUN`, and so `check_solutions`) clicks three parts on it: until it
did, every solution reported THE MACHINE NEVER LOADED, the run sitting at
state 0x8000 in front of the grid. With the clicks, 29 of 29 solve
simulated.

## The link

`tools/link.py` links all of 1.11's modules into a TIM.EXE whose program is
the original's: every byte TLINK writes, all 2758 relocations, the entry
and the stack, for the protected build and the cracked one. The object
order is a topological sort over the three orders TLINK keeps - `_DATA`,
`_BSS`, each code segment - which found gamedata.c's `_BSS` order
(`g_memory_k` after `_stklen`, `g_machine_has_bin` before `g_freeform`, no
`g_dg52e9`), compbmp.c's vector at 0x40ea, and the sound library's order.

Six bytes at the stack's top, SS:SP-6, are in the shipped file and no
linker writes them: three return addresses, left by whoever cracked it,
who ran the developer's file to unpack it, patched it and packed the memory
again with RNC. `link.py` names them (`STACK_RESIDUE`).

The last routines to match were:

- `select_puzzle_screen`: each branch of the password `if` set
  `rp_pass = 2`, and -O's cross-jumping merged them into the image's `jne`
  onto a `jmp`.
- `spread_gear_signal`: the image keeps two identical `flag = 1` stores
  that cross-jumping merges; the second is a comma expression, a different
  tree with the same bytes.
- `write_resource`: the buffer is `_DI` and the byte copy inline `asm`, as
  `emit_byte`'s huge step is in resource.c.
- `screen.c` set `second_colour` and `fill_colour` in the other order, and
  lzhuf.c's `ss:` operands are numbers: TASM made `ss:d_54e4` relative to
  `_BSS`, not DGROUP. The judge masks both kinds; only the link saw them.

## What differs from 1.00

New in 1.11, from its strings: "ADJUST PARTS BIN", "CLEAR PARTS BIN" with a
confirmation, "(Click here to enter description)", a data-disk check, the
named driver types (RESOURCE.CFG, below), `dynamix.pal`/`dynamix.scr` in place
of `sierra.*`, `gp_go.bmp`, and 560K of free memory where 1.00 wants 550K.

**A key filter**, new at 0x0905a, stands between `bios_read_key` and every
screen's key: `g_last_key` (DGROUP 0x4ef5) is now the whole word it returns,
scancode and character, and the screens test `(g_last_key & 0x7f) == 9` for
Tab where 1.00 kept one byte.

### RESOURCE.CFG

**1.11 reads RESOURCE.CFG as text**, the `key = value` lines GOG's installer
writes (`soundDrv = SBPRO.DRV`, `audioDrv = AUDBLAST.DRV`, ...), in a module
of its own: `read_resource_cfg` (0x0f0ef, `rescfg.c`). `SoundDrv` picks the
music device and `AudioDrv` the digitised module, into DGROUP 0x00fc and
0x00fa, which `game_startup` hands to `start_sound`. 1.00 read three binary
bytes of the file inside `game_startup`.

An earlier note here said 1.11 read three bytes as 1.00 did, and blamed the
text file for an emulator crash in which the Sound Blaster module's IRQ probe
restored IRQ 0's vector from a copy it never saved. The reading was wrong;
the crash is still the Sound Blaster's: the text selects SBPRO.DRV and
AUDBLAST.DRV, and the emulator has no card to answer the probe. A staged copy
of the game directory with a RESOURCE.CFG that names no driver - `00 00 fe`
serves, as no line of it is a key - runs on the speaker: the title (flip
120) and the credits (flip 450) draw, 475 flips in 250M instructions.

## History: moving the sources from 1.00

The sources were 1.00's until 2026-10-02, and were moved to 1.11 module by
module; 1.00's are kept as they were, in `reconstruct/v1.00`. What follows is
how that went.

### How far 1.00's source was from 1.11

Matched routine by routine (1.00's 1,157 public routines from the link map,
immediates, displacements, call targets and relocated words masked), in
TEMIM's image:

| | routines |
| --- | --- |
| byte-identical, moved | 160 |
| same instructions, other addresses and constants | 354 |
| the same logic compiled differently | ~570 |
| no good match | 41 |
| too short to place | 29 |

"Compiled differently" is mostly code generation, not game changes: in
`part_hit_bellow` the logic and the record offsets are the same, and 1.11
merges two identical tails and returns early, which is jump optimisation
(`-O`) or a later compiler. It is spread over every segment, part kinds
included. The 41 are mostly the compressors' writers (`lzss_flush`,
`lzw_flush`, the Huffman encoder, `insert_node`/`delete_node`), and
`part_handle_at_pointer`, `part_key_shortcut`, `settle_carried_part` and some
sound routines.

### Addresses, tools and the first modules

**Addresses.** `tools/addrmap.py` places each of 1.00's routines (read from
the sources as tagged `tim-1.00`) in 1.11: exactly, with every constant,
displacement, call target and relocated word masked, or else by resemblance -
and a resemblance may only land on **an entry of 1.11's**: a far call's
target, a near call's, a relocated far pointer to a `push bp / mov bp, sp`,
or a prologue straight after a return. Without that rule it placed a routine
at whichever instruction looked best, which put `draw_frame_corners`,
`game_teardown`, `copy_rect_around_cursor` and `select_cursor` a few bytes
into the routine before theirs; with it all four land where 1.11's callers
call. A placement is taken (`--apply`) when it is exact or resembles at 0.6
or better: 1,051 addresses in 53 files. 163 keep their 1.00 address and say
"(1.00's; not yet placed in 1.11)" beside it. Addresses mentioned in prose,
the image ranges in the file headers and the `JUDGE: data` bounds are still
1.00's: data needs a map of its own.

**The tools read the version from the image.** `tim.DGROUPS` gives each
version's DGROUP by the size of its recovered image, and `disasm.py` and the
judge take theirs from it. `tools/runtime_names.json` is regenerated for 1.11
by turboc's `libmatch.py` (82 names, `__ftoupper` new); 1.00's are kept
beside them as `names_1.00`. `tools/datamap.py` places 1.00's DGROUP objects
in 1.11 the way addrmap places routines.

**`gamemain.c` and `rescfg.c` match 1.11 too**, data included. 1.11 clears
the keyboard's lock flags at 0000:0417 (`LOW_MEMORY`, a new macro: the
host's low memory is two objects), measures free memory in thousands into
`g_memory_k` and wants 297 of them, opens the first 88 levels from the start,
defaults the master level to 4, loads `newmouse.bmp`, and takes the 180
shape records as one block.

The host starts 1.11: the Dynamix screen and the title run for 279 flips,
until `draw_rope` - still 1.00's - reaches for `g_border_art`, which 1.11
loads only after the credits.

**`intro.c` is the first module proven against 1.11**: all six routines and
its `_DATA` match, protected and cracked. 1.11 draws the Dynamix screen
(`jtp.bmp`, `dynamix.scr`, `dynamix.pal`) on a border of colour 6 - the video
driver's slot 25, `vm_set_border_colour`, which 1.00 carried a thunk for and
never called; VM.OVL is byte for byte 1.00's - holds its last frame for 0x78
ticks, preloads sounds by how much memory there is (`g_preload_sound_ids`,
`g_preload_sound_need`, `g_memory_k`), loads the panel art itself
(`newcp.bmp`, `newgpbor.bmp`), plays the credits' tunes 0x3ea..0x3fd, and
shuffles the copy-protection grid through a table.
